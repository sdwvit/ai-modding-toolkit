# Publishing: Steam Workshop, mod.io, Xbox, bug reports to GSC

Console builds are not made by modders: GSC cooks them from the mod's source zip after a request on the Zone Kit
support desk, and uploads the Xbox build to the mod's mod.io page. The same desk takes bug reports. Verified
upstream with several requests and 2 bug reports.
Adapted from the Stalker 2 modding harness (github.com/noahsemus/stalker2-modding-harness, MIT, copyright Noah Semus); this part was contributed there by sdwvit.

Versions, changelogs, zips and Nexus text: stalker2-release. Cooking and the staged output: stalker2-zonekit.

## Who does what
- Publishing is the user's act. You prepare (the zip, the texts, the list of links), check (layout, versions,
  missing-asset warnings, open tickets) and explain every step click by click. The user logs in, fills in, ticks
  and submits.
- Never ask for, read or store a password, token, API key, account name or e-mail (stalker2-workflow).
- The attestations on GSC's form are the user's own statements: show them the prepared answers and let the user
  tick and submit.

## Steam Workshop (optional; the user's clicks in the Zone Kit)
- The Zone Kit uploads by itself (its `DefaultEngine.ini` has a `[SteamWorkshop]` section with the game's app id
  1643320). Toolbar button **Steam Workshop Upload** > "Upload mod to Steam Workshop": new item or update of an
  existing one, title, description, visibility (Public / Friends / Private / Unlisted), thumbnail (under 1 MB).
- It cooks the mod currently picked in the toolbar mod selector and uploads that, so the kit must hold exactly the
  released state. Tell the user to upload only after the last change for that release is cooked and confirmed, or
  the Workshop gets an older build.
- Needs Steam running, the game owned in that Steam account, and write access to the kit folder.
- "Item with current name exists already" = choose update instead.
- A Workshop copy and a `<mods>` copy of the same mod load it twice: keep one while testing.
- The upload changes the plugin in the kit (seen upstream on one mod): the root
  `Autogenerated_<n>_WorldSubsystemData` is replaced by a new one with another number (same subsystem class), the
  kit classifier lists are rewritten (OverridePackages names the new asset) and a
  `__ModKitWwiseCookAnchor_<Mod>_<n>__` asset appears in the plugin root. All harmless; copy the kit plugin back
  into `<repo>` afterwards so the two match.

## mod.io (distribution; the Xbox build lives there too)
- The mod's page is `https://mod.io/g/<game name>/m/<slug>`, with game name `stalker2`. The slug is fixed when the
  mod is created and does not follow a rename: have the user copy the URL from the page (or take `profile_url` from
  the API). Never build it from the mod's name (two requests got wrong links that way).
- The PC file is the staged cook output: zip `<kit>/Stalker2/SavedMods/Staged/<Mod>/Windows/` so that the archive
  holds `Windows/{OverrideContent,NewContent}/Windows/...`.
- A mod's file list mixes PC builds and the Xbox builds GSC uploads: the shipped PC build is the newest file whose
  platforms include `windows` (the newest file can be Xbox-only).
- Some older mod.io zips also carry a stale pre-2.0 `Stalker2/` folder next to `Windows/`: ship only `Windows/`.
- To fetch a published build, mod.io's API is the reliable route; `steamcmd` Workshop downloads waited on Steam
  Guard approval and timed out.
- Upstream documents the API only (references/support-desk.md), not the website's clicks. API calls need the
  user's own mod.io access token: the user runs them, with the token in their own environment.
- **Unverified**: upstream's uploads tagged the PC file `platforms[] = windows, xboxseriesx`; whether
  `xboxseriesx` is needed on the PC file is not known.

## Xbox build request: before the form
1. **The mod is public on mod.io first.** The request needs the mod's public mod.io page URL.
2. **The source zip on a shareable link.** Zip the contents of the mod's plugin folder `<kit>/Stalker2/Mods/<Mod>/`
   (`<Mod>.uplugin`, `Content/` with the `.uasset`s and loose `.cfg`s, `Resources/`) at the zip root. The user
   uploads it somewhere "anyone with the link can view" (the form asks for a Google Drive URL). Asset mods reach
   about 125 MB. The request is not filed without the link.
   Mods with Wwise audio need more in the zip: references/support-desk.md.
3. **No missing-asset warnings.** If the last cook logged missing-asset warnings, sort that out first: the form
   asks the user to confirm there are none.
4. **One ticket per mod.** The user opens their tickets list (signed in) and searches for the mod name (subjects
   are usually `XBOX Mod Cooking Request: <Mod>`; check older wordings too). An OPEN ticket for the mod: send the
   update as a reply there (new zip link + mod.io link). Only closed ones: file a new request.
5. GSC replies on the ticket once the Xbox build is on mod.io; nothing else is needed.

## Bug reports to GSC
Same support desk, another category. Write it as a reproducible game or kit bug: what you did, what happened, what
should happen, kit and game version, logs. Fields and limits: references/support-desk.md. Crash triage before
reporting: stalker2-crashes.

## Traps
- Never resubmit a request that went through, even to fix its subject.
- On the form, the category is picked first: the mod fields only appear after it.
- The form page can look signed out while the ticket still lands on the account: judge sign-in from the tickets
  list.
- Linux: nothing differs. The desk, mod.io and the upload were all used from a Linux browser and shell.

Read references/support-desk.md before preparing an Xbox build request or a bug report for the user (where the
form is, every field, what happens after Submit), and before describing the mod.io API.
